# HyperCube `/server-2d` Handoff

## 목적

이 문서는 HyperCube의 단일 서버 2D 관제 페이지(`/server-2d`) 작업을 Claude Code에게 정확히 넘기기 위한 인수인계 문서다.

핵심은 다음 한 줄이다.

`/admin/dashboard`는 절대 건드리지 말고, `/server-2d`를 단일 서버 2D 관제 페이지로 완성해야 한다.

---

## 절대 조건

### 1. 건드리면 안 되는 페이지

- `/admin/dashboard` 절대 수정 금지
- 사용자가 현재 `/admin/dashboard`를 직접 다시 작업 중임
- 전체 서버/전체 Agent 통합 관제는 `/admin/dashboard` 역할임

### 2. 작업 대상 페이지

- 새 페이지 대상: `/server-2d`
- URL 예시: `http://192.168.0.63:3000/server-2d`
- 이 페이지는 `서버 1대`를 깊게 보는 2D 관제 화면이어야 함

### 3. 데이터 원칙

- 기존 3D 화면에서 쓰는 데이터를 최대한 재활용해야 함
- 3D를 없앤다고 데이터가 줄어들면 안 됨
- 서버 자원 + 스택 + 전체 컨테이너 상태 + 과거 추이 + 최신 갱신까지 다 보여줘야 함

---

## 사용자가 요청한 요구사항 전체 정리

## A. 화면 목적

사용자는 이 페이지를 단순한 시각화가 아니라 `모니터링 시스템`으로 원함.

즉:

- 이 페이지 하나만 띄워도 해당 서버 현황을 한눈에 파악할 수 있어야 함
- 특히 아래 두 가지가 가장 중요함
  - 서버 자원 상태
  - 각 컨테이너 상태

---

## B. UI/UX 요구사항

### 1. 한눈에 현황 파악 가능해야 함

- 스크롤 내려가며 찾는 구조를 싫어함
- 아래로 스크롤하지 않고도 핵심 현황이 보여야 함
- 정보가 빈약하면 안 됨
- “적당히 예쁜 화면”보다 “운영자가 빨리 읽히는 화면”이어야 함

### 2. 한국어 UI

- 기능명, 제목, 레이블 전부 한국어

### 3. 비전공자도 이해 가능해야 함

- 각 카드/그래프/지표마다 `?` 툴팁 필요
- 툴팁 내용은 비전공자도 이해 가능한 수준으로 짧고 명확해야 함

### 4. 대량 컨테이너도 깨지면 안 됨

- 실제 16번 서버처럼 컨테이너가 많아도 UI가 깨지면 안 됨
- 데모 서버도 많은 데이터를 넣어도 보기 쉬워야 함
- “많을 때도 정상 동작”이 필수 조건임

---

## C. 데이터/기능 요구사항

### 1. 서버 전환이 제대로 되어야 함

사용자 질문:

- “서버 바꿨을 때 왜 제대로 작동 안 해?”

즉 다음이 필요함:

- 서버 선택 시 실제 데이터 소스가 확실히 바뀌어야 함
- 이전 서버 데이터가 남아 있으면 안 됨
- 실시간 데이터/과거 데이터/차트/컨테이너 목록이 모두 서버 기준으로 동기화돼야 함

### 2. 더미 서버 필요

사용자 요청:

- “데이터들이 잔뜩 있는 더미 서버도 하나 넣어줘”

의미:

- 단순 몇 개 컨테이너 수준이 아니라 밀도 테스트 가능한 데모 서버 필요
- 스택도 여러 개여야 함
- 상태도 running만 있으면 안 됨
- paused / restarting / exited / problem 상태도 섞여야 함
- 네트워크/볼륨/지표 변동도 있어야 함

### 3. 과거 데이터 + 최신 데이터 갱신 필요

사용자 불만:

- 추이 안 보임
- 과거 데이터 없음
- 최신 데이터 갱신도 안 됨

즉:

- 과거 히스토리 필요
- 선택 범위별 polling 필요
- 실시간 또는 준실시간 갱신이 계속 보여야 함

---

## D. 차트/시각화 요구사항

### 1. 스택 평균 라인 그래프

이 요구는 매우 중요하며 오해하면 안 됨.

사용자가 원하는 것은:

- 컨테이너별 여러 라인 아님
- 스택은 컨테이너 그룹임
- 따라서 `각 스택의 평균값`으로 선을 만들어야 함
- 그리고 `한 그래프 안에 모든 스택`이 같이 들어가야 함

즉 사용자가 원하는 최종 형태:

- CPU 그래프 1개
  - 모든 스택 평균 CPU 선 포함
- 메모리 그래프 1개
  - 모든 스택 평균 메모리 선 포함
- GPU 그래프 1개
  - 가능하면 모든 스택 평균 GPU 선 포함
- 네트워크 그래프 1개
  - 가능하면 모든 스택 평균 네트워크 선 포함

중요:

- 지표 토글형 1그래프가 아니라 `지표별 별도 그래프`
- 각 그래프 안에는 `모든 스택 레전드`
- Chart.js 사용 선호

### 2. 산점도

- 라이브러리 써서 만들 것
- 직접 대충 SVG 점 몇 개 찍는 느낌이면 안 됨
- CPU vs Memory 같은 분포를 운영자가 읽기 쉽게 표현할 것

### 3. 열지도

사용자 불만:

- “열지도도 지금 짜치네”
- “많을 때를 항상 생각하고 전부 검토해”
- “데모 서버도 제대로 나오지도 않고 보기도 힘들다”

즉:

- 상위 10개, 상위 24개만 자르는 방식은 부족함
- 전체 컨테이너를 스택 단위나 그룹 단위로 읽기 쉽게 보여주는 구조 필요
- 대량 컨테이너에서도 밀도와 가독성 둘 다 잡아야 함
- 보기가 쉬워야 하고, 장식보다 판독성이 우선

### 4. 프레임 다이어그램

사용자 반응:

- “프레임 다이어그램이 없는데 뭐가 돼?”
- “보통 이렇게 만드나? 라이브러리 쓴 거 맞어?”

즉:

- 프레임 다이어그램은 존재감이 확실해야 함
- 사용자가 봤을 때 “이게 프레임 다이어그램이구나” 해야 함
- 단순 점 몇 개나 약한 도식은 불만족
- 라이브러리를 쓴다고 끝이 아니라, 구조적으로 읽혀야 함

---

## E. 시간 범위 요구사항

사용자는 아래 범위를 직접 지정했고, 이 규칙에 맞게 동작하길 원함.

| 범위 | Polling | Bucket | Points | 표시 창 | Backend API 매핑 |
|---|---:|---:|---:|---|---|
| 1m | 10초 | 5초 | 30 | 약 2분 30초 | 5m 요청 후 최근분 필터 |
| 5m | 30초 | 15초 | 60 | 과거 15분 | 5m |
| 1h | 1분 | 60초 | 240 | 과거 4시간 | 1h |
| 24h | 5분 | 5분 | 500 | 약 41시간 | 24h |
| 7d | 30분 | 30분 | 600 | 약 12.5일 | 24h fallback |

의미:

- 화면에서 범위 선택 가능해야 함
- polling 주기가 범위마다 달라야 함
- bucket 집계도 범위마다 달라야 함
- 차트 point 수도 범위마다 달라야 함
- 과거 데이터 양도 범위별로 다르게 가져와야 함

## 현재 반영된 것

- `/server-2d` 신규 페이지 존재
- 서버 선택 로직 존재
- 더미 서버 존재
- 시간 범위 선택 존재
- 스택 평균 차트 구조 일부 존재
- 산점도/프레임/열지도 관련 컴포넌트 존재

## 아직 부족하거나 재검토 필요한 것

### 1. 프레임 다이어그램 품질

- 라이브러리를 썼더라도 결과물이 사용자가 기대하는 “프레임 다이어그램”인지 재검토 필요
- 더 구조적이고 더 읽기 쉬운 방식으로 바꿔야 할 수 있음

### 2. 열지도 품질

- 많은 컨테이너에서 충분히 읽히는지 실검증 필요
- 데모 서버 기준으로도 보기 좋은지 다시 봐야 함

### 3. 16번 서버 실검증

- 가장 중요
- 실제 많은 컨테이너 서버에서 깨짐 여부를 브라우저로 직접 확인하고 맞춰야 함
- 코드만으로 “아마 될 것”이면 안 됨

### 4. GPU 스택 평균 그래프

- 현재 백엔드 컨테이너 히스토리 API 기준으로 스택/컨테이너 GPU 히스토리가 없을 가능성이 큼
- 이 경우:
  - 프론트에서 억지 추정으로 속이지 말 것
  - 백엔드 지원 필요 여부를 명확히 보고할 것

## Claude Code가 해야 할 일

## 1. 가장 먼저 할 것

- `/admin/dashboard`와 관련된 파일은 건드리지 말 것
- `/server-2d`만 작업할 것
- 실제로 `/server-2d`를 브라우저에서 열고 확인할 것

## 2. 필수 작업

- 스택 평균 차트를 지표별 멀티 그래프로 완성
- Chart.js 기반 품질 개선
- 산점도 라이브러리 기반 품질 개선
- 프레임 다이어그램을 더 표준적이고 읽기 쉬운 구조형 시각화로 개선
- 열지도를 대량 컨테이너에서도 읽기 쉬운 형태로 재구성
- 16번 서버 기준 UI 깨짐 수정
- 데모 서버도 밀도 테스트용으로 충분히 보기 좋게 개선
- 시간 범위별 polling / bucket / points / window 규칙 준수

## 3. 검증

- `http://192.168.0.63:3000/server-2d` 실제 확인
- 로그인 후 실제 서버 선택 테스트
- 16번 서버 테스트
- 데모 서버 테스트
- 많은 컨테이너 수에서 레이아웃 검증
- 차트가 비어 보이거나 범례가 읽기 어려운지 확인

## 최종 인수 기준

아래가 만족돼야 “끝났다”고 볼 수 있다.

- `/admin/dashboard` 미수정
- `/server-2d`만 수정
- 서버 전환 정상 동작
- 더미 서버 제공
- 많은 컨테이너에서도 UI 안 깨짐
- 한 화면에서 서버 자원/스택/컨테이너 현황이 빠르게 읽힘
- 스택 평균 그래프가 지표별로 분리되고 모든 스택 선이 같이 보임
- 열지도와 프레임 다이어그램이 존재감 있고 실제로 읽힘
- 시간 범위별 히스토리/polling 동작
- 툴팁/한국어 UI 유지
