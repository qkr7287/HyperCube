1. 배경 — HyperCube 가 무엇인가

HyperCube 는 GPU 호스트를 다수 사용자에게 컨테이너 단위로 할당하는 GPU workstation 임대 플랫폼. Paperspace / RunPod / Vast.ai 와 동일한 모델. K8s 같은 service orchestration 이 아님.

  • 사용자 1명 ↔ 컨테이너 1개 매핑
  • 사용자는 컨테이너 안에서 Jupyter / ssh / terminal 로 작업
  • GPU slice (MIG 또는 통째) 가 컨테이너에 할당
  • 구조: backend (Django, scheduler/API) + agent (per-host, docker control) + container

현재 문제 — 자원 한도 미적용

  • 컨테이너 생성 시 CPU / 메모리 / 디스크 한도 명시 안 함 → host 전체 공유
  • 한 사용자가 host 자원 다 점유 가능 → noisy neighbor / OOM
  • 한 사용자가 host 디스크 채우면 docker daemon 까지 죽음
  • KPI 의 "X% 사용" 이 분모 (quota) 가 없어서 운영자 직관과 불일치

해결 방향

  • 컨테이너 생성 시 cpuQuota / memory hard limit 적용 (cgroup)
  • 워크스페이스 디스크 = LVM thin volume per-container (block-level 격리, MIG 단절)
  • 데이터셋 / 모델 = NFS read-only mount (공유)
  • backend 가 추천값을 동적 계산하려면 agent 가 host capacity 보고 필요

2. 이번에 해야 할 일 (overview)

#기능요약우선순위
1 capacity_report 메시지 agent 시작 시 + 1시간 주기로 host 정적 사양 보고 P0 (필수)
2 create_container HostConfig 확장 backend 가 전달한 memory / cpuQuota 를 Dockerode 에 적용 P0
3 LVM thin volume 관리 컨테이너 생성/삭제 시 lvcreate / mkfs / mount / lvremove P0
4 workspace 디스크 사용량 보고 주기적 df 또는 lvs → backend P1
5 install script 확장 설치 시 LVM thin pool 자동 셋업 + NFS mount P0
전체 모습 
backend → agent: create_container {
  image, name, env, ports, ...,
  hostConfig: { memory, memorySwap, cpuQuota, cpuPeriod, oomKillDisable: false },
  workspace: { sizeGb, mountTarget: "/workspace" }
}

agent ↓
  1. lvcreate -V {sizeGb}G -T vg0/thin_pool -n cid_{cid}
  2. mkfs.ext4 /dev/vg0/cid_{cid}
  3. mount /dev/vg0/cid_{cid} /var/lib/hypercube/workspaces/{cid}
  4. docker createContainer({ HostConfig: {Memory, CpuQuota, ...,
       Binds: ["/var/lib/hypercube/workspaces/{cid}:/workspace",
               "/mnt/datasets:/datasets:ro",
               "/mnt/models:/models:ro"]
     }})
  5. docker start
  6. backend ← create_container_result { ok, workspace.device, workspace.mountPoint }

3. 신규 1 — capacity_report 메시지

backend 가 추천 자원 한도를 host 사양에 동적으로 맞추려면 agent 가 정적 capacity 를 보고해야 함. (시계열 메트릭 system_metrics 와 별개)

3.1 언제 보내나

  • agent 시작 직후 (backend WebSocket 연결 성공 시 1회)
  • 이후 1시간 주기 (host 사양 변경 — RAM 추가, 디스크 교체 등 — 인지용)
  • 또는 backend 가 request_capacity 명령 보낼 때 on-demand

3.2 메시지 포맷

4. 신규 2 — create_container HostConfig 확장

backend 가 create_container 명령에 자원 한도 옵션을 추가 전달.

4.1 메시지 포맷 변경

// backend → agent
{
  "type": "create_container",
  "requestId": "req-...",
  "data": {
    "image": "hypercube/ml-pytorch-jupyter:cuda12.4-airgap",
    "name": "ops-flow-1",
    "env": { ... },
    "ports": { ... },
    "gpus": ["GPU-uuid-..."],

    // 신규 — 자원 한도
    "hostConfig": {
      "memory":         17179869184,           // bytes (= 16 GB)
      "memorySwap":     17179869184,           // swap 비활성 (limit == swap)
      "cpuQuota":       400000,                // microseconds (4 cores = 4 * 100000)
      "cpuPeriod":      100000,                // 100 ms (default)
      "oomKillDisable": false
    },

    // 신규 — workspace LVM thin volume
    "workspace": {
      "sizeGb": 100,
      "mountTarget": "/workspace"
    },

    // 신규 — NFS 공유 mount
    "sharedMounts": [
      {"source": "/mnt/datasets", "target": "/datasets", "readOnly": true},
      {"source": "/mnt/models",   "target": "/models",   "readOnly": true}
    ]
  }
}

4.2 Dockerode 매핑

// agent 측
const hostConfig = {
  "Memory":         data.hostConfig.memory,
  "MemorySwap":     data.hostConfig.memorySwap,
  "CpuQuota":       data.hostConfig.cpuQuota,
  "CpuPeriod":      data.hostConfig.cpuPeriod,
  "OomKillDisable": data.hostConfig.oomKillDisable,
  "Binds": [
    `${workspaceDevice}:${data.workspace.mountTarget}:rw`,
    ...data.sharedMounts.map(m => `${m.source}:${m.target}:${m.readOnly ? 'ro' : 'rw'}`)
  ],
  // 기존 옵션 (NetworkMode, RestartPolicy, GPU device 등) 유지
};

await docker.createContainer({
  "Image": data.image,
  "name": data.name,
  "Env": ...,
  "HostConfig": hostConfig,
  ...
});

4.3 update-limits 명령 (이미 존재)

backend 의 update-limits action 이 이미 있음 (docker update live). 이 부분은 기존대로 동작 — Dockerode container.update({Memory, CpuQuota}) 그대로. HostConfig 가 create 시 잡혀있어도 update 가능.

5. 신규 3 — LVM thin volume 관리

컨테이너 생성/삭제 시 workspace 가상 disk 를 동적 생성. 컨테이너는 자기 가상 disk 만 봄 (host 파일시스템 안 보임). MIG 가 GPU 를 partition 하듯 LVM thin 이 디스크를 block-level partition.

5.1 생성 흐름 (create_container 안에서)

// agent 의 create_container handler 안
const cid = container.id.slice(0, 12);       // e.g. "05eddec05865"
const volumeName  = `cid_${cid}`;
const volumePath  = `/dev/vg0/${volumeName}`;
const mountPoint  = `/var/lib/hypercube/workspaces/${cid}`;

// 1. thin volume 생성
await exec(`lvcreate -V ${data.workspace.sizeGb}G -T vg0/thin_pool -n ${volumeName}`);

// 2. filesystem 생성 (ext4 권장)
await exec(`mkfs.ext4 -F ${volumePath}`);

// 3. mount point 생성 + mount
await exec(`mkdir -p ${mountPoint}`);
await exec(`mount ${volumePath} ${mountPoint}`);

// 4. ownership — 컨테이너 내부 사용자에 맞춰 (jovyan = 1000:100 등)
await exec(`chown ${UID}:${GID} ${mountPoint}`);

// 5. docker createContainer 의 Binds 에 mountPoint 추가
hostConfig.Binds.push(`${mountPoint}:${data.workspace.mountTarget}:rw`);

// 6. backend 에 결과 보고
sendMessage({
  "type": "create_container_result",
  "data": {
    "ok": true,
    "containerId": container.id,
    "workspace": {
      "device": volumePath,
      "mountPoint": mountPoint,
      "sizeGb": data.workspace.sizeGb
    }
  }
});

5.2 삭제 흐름 (remove_container 안에서)

// 1. docker container 제거
await docker.getContainer(cid).remove({force: true});

// 2. mount 해제
await exec(`umount ${mountPoint}`);
await exec(`rmdir ${mountPoint}`);

// 3. thin volume 제거
await exec(`lvremove -f vg0/${volumeName}`);

5.3 thin pool 모니터링

thin pool 은 over-provision 가능 → 실제 채워지면 모든 volume 이 read-only 로 떨어짐. 사전 알림 필수.

  • lvs --units g vg0/thin_pool 결과의 Data% 가 80% 이상 → backend 에 warn 보고
  • 90% 이상 → critical alert (즉시 admin 알림)
  • capacity_report 와 별개로 system_metrics 메시지에 lvm.thinPool.usedPct 필드 추가 권장

6. 신규 4 — workspace 디스크 사용량 보고

각 컨테이너의 workspace volume 사용량을 주기적으로 보고. backend 의 KPI 카드에 표시.

6.1 메시지 — 기존 container_metrics 확장

// agent → backend, 컨테이너 별 주기적 push
{
  "type": "container_metrics",
  "data": {
    "containerId": "05eddec05865",
    "cpu": { ... },
    "memory": { ... },
    "network": { ... },
    "disk": { ... },

    // 신규 — workspace volume 사용량
    "workspace": {
      "device":       "/dev/vg0/cid_05eddec05865",
      "sizeGb":       100,
      "usedGb":       12,                   // df -B1G {mountPoint} 의 used
      "availableGb":  88,
      "usedPct":      12.0
    }
  }
}

6.2 수집 방법

  • df -B1G {mountPoint} 출력 파싱 — 가장 단순
  • 또는 lvs --units g {volume} 의 Data% — thin volume 의 실제 점유
  • 수집 주기 = 기존 container_metrics 주기 (보통 10~30초) 와 동일

7. 신규 5 — install script 자동화

host 추가 시 운영자가 LVM 수동 셋업 안 하도록, agent install script 가 자동 처리. "curl ... | sudo bash" 한 줄.

7.1 install 흐름

#!/bin/bash
# curl -fsSL https://hypercube.example/install.sh | sudo bash -s -- \
#   --backend-url wss://backend/ws \
#   --token AGENT_TOKEN \
#   --nfs-server 192.168.0.10 \
#   --thin-pool-size 80%

set -e

# 1. 패키지 — Node.js, lvm2, nfs-common, ethtool, util-linux
apt-get update
apt-get install -y nodejs lvm2 nfs-common ethtool

# 2. LVM thin pool 자동 셋업 — 기존 vg0/thin_pool 없을 때만
if ! lvs vg0/thin_pool >/dev/null 2>&1; then
  # /dev/sdb 또는 free space 자동 감지 (별도 로직)
  pvcreate /dev/sdb
  vgcreate vg0 /dev/sdb
  lvcreate -L 80%VG -T vg0/thin_pool
fi

# 3. NFS mount /mnt/datasets, /mnt/models (read-only)
mkdir -p /mnt/datasets /mnt/models
echo "${NFS_SERVER}:/datasets /mnt/datasets nfs ro,noauto,x-systemd.automount 0 0" >> /etc/fstab
echo "${NFS_SERVER}:/models   /mnt/models   nfs ro,noauto,x-systemd.automount 0 0" >> /etc/fstab
mount /mnt/datasets
mount /mnt/models

# 4. workspace mount base
mkdir -p /var/lib/hypercube/workspaces

# 5. agent 설치 — systemd 등록
curl -fsSL .../agent.tar.gz | tar -xz -C /opt/hypercube-agent
cat > /etc/systemd/system/hypercube-agent.service <<EOF
[Service]
ExecStart=/opt/hypercube-agent/agent
Environment=BACKEND_URL=${BACKEND_URL}
Environment=AGENT_TOKEN=${AGENT_TOKEN}
User=root
EOF
systemctl enable --now hypercube-agent

# 6. agent 시작 → backend 에 capacity_report 자동 전송

7.2 운영자가 결정하는 것

  • NFS server 주소 (--nfs-server)
  • thin pool 크기 비율 또는 절대값 (default 80%)
  • agent token (backend 에서 발급)

그 외 모두 자동.

8. 권한 / 보안

agent 가 root 권한 필요 — lvcreate, mkfs, mount, umount, lvremove 는 root 만 가능.

8.1 옵션 비교

옵션설명장점단점
(A) agent process 자체가 root systemd User=root 단순, 권한 issue 없음 process 전체가 root 권한 → 보안 영향
(B) sudo 화이트리스트 agent 는 일반 user, /etc/sudoers.d/hypercube-agent 에 lvcreate 등만 NOPASSWD 최소 권한 원칙 sudo 매번 호출 overhead, 설정 복잡
(C) helper binary (setuid) agent → small helper binary (root setuid) → lvcreate 최소 권한, 명령 화이트리스트 강제 helper 코드 추가 작업

권장: (A) — 단순함 우선. agent host 는 backend 가 신뢰하는 인프라. multi-tenant 아님 (agent 자체는 한 호스트만 관리). 다만 install script 와 agent code 가 audit 가능해야.

8.2 명령 인젝션 방지

  • 모든 exec 호출은 array form 사용 (execFile) — shell 통해 X
  • cid, volumeName 은 backend 에서 받지만 정규식 validate (^[a-f0-9]{12}$)
  • size 도 정수 validate

9. 실패 시나리오 / rollback

9.1 생성 중 실패

실패 단계처리
lvcreate 실패 (thin pool full) backend 에 result.ok=false + reason="thin_pool_full" 보고. backend 가 사용자에 안내
mkfs 실패 lvremove 로 rollback → result.ok=false
mount 실패 lvremove → rollback
docker createContainer 실패 umount + lvremove → rollback
docker start 실패 docker remove + umount + lvremove → rollback

9.2 운영 중 발생

  • OOM kill — Docker event 로 감지 → backend 에 event 보고 (기존 흐름)
  • thin pool 90%+ — capacity_report / system_metrics 로 알림
  • volume corruption — agent 가 mount 실패 감지 → backend 에 보고, 사용자 알림 + admin 개입

9.3 agent 재시작 / host reboot

  • 기존 volume 들이 host reboot 후 살아있는지 확인 (lvs)
  • mount 가 fstab 또는 systemd mount unit 으로 등록되어야 자동 재마운트
  • 또는 agent 시작 시 active container 의 workspace 들 자동 remount
