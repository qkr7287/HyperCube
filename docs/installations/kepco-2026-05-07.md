## 2. 설치 방법 — 왜 비표준 절차로 했나

가져간 인스톨러는 **24.04용 (`hypercube-1.0-ubuntu2404.sh`)**이었으나 서버 OS는 **22.04**.

→ 정공법 인스톨러 실행 시 codename 검증(`noble`)에서 거부됨.
→ 다행히 **Docker 29.2.1이 사전 설치**되어 있어서, 24.04용 인스톨러의 **이미지 tar만 추출**해서 활용했음 (24.04용 Docker `.deb`은 무시 — 22.04 라이브러리와 충돌 위험).

이 방법은 컨테이너 이미지가 호스트 OS와 무관하기 때문에 가능.

## 3. 실행한 명령 (재현용)

```bash
# 1. .sh 압축만 풀기 (실행 안 함)
cd /data/hypercube/260507/Main/
sudo bash ./hypercube-1.0-ubuntu2404.sh --noexec --target ./hc-extracted

# 2. 이미지 4개 import (backend, nginx, postgres, redis)
sudo docker load -i ./hc-extracted/images/hypercube-images.tar

# 3. /opt/hypercube/ 만들고 compose 파일 복사
sudo mkdir -p /opt/hypercube
sudo cp ./hc-extracted/app/docker-compose.yml /opt/hypercube/
sudo cp ./hc-extracted/app/.env.example /opt/hypercube/

# 4. .env 생성 (인터랙티브)
sudo bash ./hc-extracted/env-generate.sh /opt/hypercube/.env

# 5. 컨테이너 시작
cd /opt/hypercube
sudo docker compose up -d

# 6. systemd unit 등록
sudo cp /data/hypercube/260507/Main/hc-extracted/app/hypercube.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable hypercube

# 7. 헬스체크
curl http://localhost:7003/api/health/
# {"status": "ok"}
```

## 6. 운영 명령

### 시작 / 중지 / 재시작

```bash
sudo systemctl start hypercube       # 시작
sudo systemctl stop hypercube        # 중지
sudo systemctl restart hypercube     # 재시작
sudo systemctl status hypercube      # 현재 상태
```

### 설정 변경

```bash
sudo nano /opt/hypercube/.env
sudo systemctl restart hypercube
```

⚠️ `DB_PASSWORD`는 첫 부팅에만 적용됨 (postgres가 그때 사용자 생성). 나중에 바꾸려면 별도 절차 필요.

### DB 백업

```bash
sudo docker compose -f /opt/hypercube/docker-compose.yml exec -T postgres \
    pg_dump -U hypercube hypercube > /data/hypercube/backups/$(date +%Y%m%d).sql
```

### DB 복원

```bash
cat /data/hypercube/backups/20260507.sql | \
    sudo docker compose -f /opt/hypercube/docker-compose.yml exec -T postgres \
    psql -U hypercube hypercube
```

## 7. 이상 발생 시 — 로그 보는 순서

> 어디서 막혔는지 모를 땐 **위에서 아래로 차례로 확인**하면 됩니다.

### 7-1. 가장 먼저 — 컨테이너 상태

```bash
sudo docker compose -f /opt/hypercube/docker-compose.yml ps
```

| 보이는 상태 | 해석 |
|----------|------|
| 6개 모두 `Up X minutes` 또는 `(healthy)` | 정상 |
| 일부가 `Restarting` | 7-2로 |
| `Exited (N)` | 7-2로 |

### 7-2. 죽거나 재시작 중인 컨테이너의 로그

문제 있는 서비스 이름을 `<svc>` 자리에 넣어서:

```bash
sudo docker compose -f /opt/hypercube/docker-compose.yml logs --tail 100 <svc>
```

서비스 이름:
- `backend` (가장 흔함 — DB 연결, migration 등)
- `postgres`
- `redis`
- `nginx`
- `celery-worker`
- `celery-beat`

예:
```bash
sudo docker compose -f /opt/hypercube/docker-compose.yml logs --tail 100 backend
```

### 7-3. 실시간으로 보기 (꼬리 따라가기)

```bash
sudo docker compose -f /opt/hypercube/docker-compose.yml logs -f
# 또는 특정 서비스만
sudo docker compose -f /opt/hypercube/docker-compose.yml logs -f backend
```

`Ctrl + C`로 종료.

### 7-4. systemd 자체 문제면

```bash

sudo journalctl -u hypercube -n 100 --no-pager
```

### 7-5. Docker daemon 자체 문제면

```bash

sudo journalctl -u docker -n 100 --no-pager
```

### 7-6. Agent 로그 (agent 깔린 서버에서)

```bash
sudo docker logs --tail 100 hypercube-agent
sudo docker logs -f hypercube-agent      # 실시간
```

## 8. 흔한 문제 → 해결 명령 (빠른 참고)

자세한 건 `docs/runbooks/airgap-install.md` §10 참고.

| 증상 | 1차 진단 명령 | 빠른 해결 |
|------|--------------|----------|
| `hc-backend` Restarting | `docker compose logs --tail 50 backend` | 로그 안 키워드 매칭 (§7-2) |
| `password authentication failed` | (위와 동일) | `docker compose down -v` 후 `systemctl restart hypercube` ⚠️ DB 데이터 사라짐 |
| nginx 502 | backend 죽은 상태 | 7-2 |
| 외부 PC에서 `Bad Request 400` | `cat /opt/hypercube/.env \| grep ALLOWED_HOSTS` | `.env`의 `DJANGO_ALLOWED_HOSTS`에 외부 IP 추가 → restart |
| Agent가 안 붙음 | `docker logs --tail 50 hypercube-agent` | URL이 `ws://`로 시작하는지 + IP 정확한지 |
| 디스크 가득 | `df -h` | `docker system prune -a -f` (사용 안 하는 이미지/컨테이너만) |

## 9. 개발팀에 보고할 때 — 진단 패키지 만들기

§7~§8로 풀리지 않으면 **자동 진단 명령 한 줄**로 모든 정보 한꺼번에 모아서 USB로 전달.

상세: `docs/runbooks/airgap-install.md` §11

요약:
```bash
# 한전 서버에서 실행 (그대로 복붙)
sudo bash -c '
TS=$(date +%Y%m%d-%H%M%S)
DIR=/tmp/hc-diag-$TS
mkdir -p $DIR && cd $DIR
{
  echo "=== os ==="; lsb_release -a 2>/dev/null
  echo "=== disk ==="; df -h
  echo "=== mem ==="; free -h
  echo "=== docker ==="; docker version 2>&1; docker ps -a
} > 01-system.txt
cd /opt/hypercube && docker compose ps > $DIR/02-compose.txt 2>&1
mkdir -p $DIR/logs
for s in postgres redis backend nginx celery-worker celery-beat; do
  docker compose -f /opt/hypercube/docker-compose.yml logs --tail 500 --no-color $s \
    > $DIR/logs/$s.log 2>&1
done
docker logs --tail 500 hypercube-agent > $DIR/logs/agent.log 2>&1 || true
sed -E "s/^(.*PASSWORD|.*KEY|.*TOKEN|.*SECRET)=.*/\1=***REDACTED***/i" \
  /opt/hypercube/.env > $DIR/03-env-redacted.txt 2>/dev/null
journalctl -u hypercube -n 100 --no-pager > $DIR/04-journal.txt 2>&1
cd /tmp && tar czf hc-diag-$TS.tar.gz hc-diag-$TS/
ls -lh /tmp/hc-diag-$TS.tar.gz
echo "→ /tmp/hc-diag-$TS.tar.gz 를 USB로 가져가서 개발팀에 전달"
'
```

## 11. 다음 방문 시 — 업데이트 절차

새 버전 `.sh`를 가져와서 적용하는 흐름. 한전 환경은 **22.04/24.04 통합 단일 `.sh`** 받아오면 다음 방법으로 처리됩니다.

### 11-1. 표준 절차 (통합 `.sh` 받았을 때 — 권장)

통합 `.sh`는 codename(jammy/noble)을 자동 감지하므로 기존 설치 위에 **그대로 한 번 실행**하면 됩니다. 기존 `.env`와 DB 데이터는 보존됩니다.

```bash
# 1. DB 백업 (안전장치 — 항상 먼저)
sudo mkdir -p /data/hypercube/backups
sudo docker compose -f /opt/hypercube/docker-compose.yml exec -T postgres \
    pg_dump -U hypercube hypercube \
    > /data/hypercube/backups/before-update-$(date +%Y%m%d-%H%M%S).sql
ls -lh /data/hypercube/backups/

# 2. 새 .sh 가져오기 (USB → 적당한 폴더)
sudo cp /media/usb/hypercube-X.Y-ubuntu.sh /data/hypercube/
sudo chmod +x /data/hypercube/hypercube-X.Y-ubuntu.sh

# 3. 한 줄 실행
sudo /data/hypercube/hypercube-X.Y-ubuntu.sh
```

이 한 번 실행이 자동으로 다음을 합니다:
- codename 감지 → 22.04(jammy)면 jammy용 .deb (이미 docker 있으면 skip)
- 새 이미지 4개 docker load
- `/opt/hypercube/.env` 보존 ("`already exists — keeping current`" 메시지)
- `docker compose up -d`로 새 이미지 사용해 재시작
- systemd unit 갱신

### 11-2. 헬스체크

```bash
curl http://localhost:7003/api/health/
sudo docker compose -f /opt/hypercube/docker-compose.yml ps
```

6개 컨테이너 모두 `Up (healthy)` + `{"status": "ok"}` 나오면 끝.

### 11-3. 옛 docker 이미지 정리 (선택, 디스크 절약)

업데이트 후 옛 버전 이미지가 안 쓰는데 디스크에 남아있을 수 있습니다.

```bash
# 사용 중이지 않은 이미지 확인 (지우기 전 dry-run)
sudo docker images | grep -E "hypercube|pgvector|redis"

# 정리 (사용 중인 컨테이너의 이미지는 자동으로 보호됨)
sudo docker image prune -a -f
```

### 11-4. 만약 표준 절차로 잘 안 될 때 — 수동 업데이트

install.sh가 어떤 이유로 실패하거나, 설정 변경이 큰 업데이트 (예: compose 파일 구조 변경) 일 때.

```bash
# 1. 새 .sh 압축만 풀기
sudo bash /data/hypercube/hypercube-X.Y-ubuntu.sh \
    --noexec --target /data/hypercube/hc-extracted-new

# 2. 컨테이너 정지 (DB는 볼륨에 보존됨)
cd /opt/hypercube
sudo docker compose down

# 3. 새 이미지 load
sudo docker load -i /data/hypercube/hc-extracted-new/images/hypercube-images.tar

# 4. compose 파일 교체 (.env는 그대로 두기)
sudo cp /data/hypercube/hc-extracted-new/app/docker-compose.yml /opt/hypercube/

# 5. 재시작
sudo docker compose up -d

# 6. 헬스체크
curl http://localhost:7003/api/health/
```

### 11-5. Agent 업데이트

Agent가 깔린 서버들에서 새 `hypercube-agent-installer-X.Y.Z.sh`를 받아 동일하게 한 번 실행:

```bash
sudo /data/hypercube/hypercube-agent-installer-X.Y.Z.sh
```

기존 `.env`는 보존되므로 인터랙티브 prompt에서 그냥 엔터 5번 + 마지막 확인 Y 치면 됩니다 (또는 Backend WS URL이 바뀌었으면 그것만 새 값 입력).

### 11-6. 옛 작업 폴더 정리 (선택)

설치 시 만든 `hc-extracted/` 폴더는 디스크만 차지하니 원하면 지워도 됩니다 (`/opt/hypercube/`는 건드리지 마세요):

```bash
# 옛 추출 폴더 삭제
sudo rm -rf /data/hypercube/260507/Main/hc-extracted/

# 옛 .sh 파일도 (다음 업데이트 시 새 .sh로 교체될 거라)
sudo rm -f /data/hypercube/260507/Main/hypercube-1.0-ubuntu2404.sh

# 새 hc-extracted-new도 update 후 정리
sudo rm -rf /data/hypercube/hc-extracted-new/
```

### 11-7. 롤백 — 업데이트 후 문제 생겼을 때

```bash
# 1. DB 복원 (백업 SQL이 있다면)
cd /opt/hypercube
sudo docker compose down -v   # ⚠️ 현재 DB 삭제
sudo docker compose up -d postgres
sleep 10
cat /data/hypercube/backups/before-update-YYYYMMDD-HHMMSS.sql | \
    sudo docker compose exec -T postgres psql -U hypercube hypercube

# 2. 옛 이미지 태그가 남아있으면 그걸로 다시:
sudo docker images | grep hypercube-backend
# 옛 image id 확인 후 .env에서 IMAGE_TAG 박거나
# 또는 옛 .sh 파일을 보관해뒀다면 그걸로 다시 실행
```

> 안전한 롤백 보장하려면 **업데이트 전 DB 백업과 옛 `.sh` 파일을 같이 USB에 보관**해두세요.
