기획 설계 단계 v0.3 agent 자동 셋업

컨테이너 자원 한도 + 템플릿 기반 추천

HyperCube 의 본질은 GPU workstation 임대. 사용자 1명에게 컨테이너 1개를 할당, 그 안에서 작업. K8s 같은 service orchestration 이 아님 (Paperspace / RunPod / Lambda Labs 와 동일한 모델). 현재는 CPU·메모리·디스크 한도가 미설정(unlimited) 이라 noisy-neighbor 위험 + KPI 의 의미 약화. 템플릿별 권장 한도 + workspace 디스크 격리 (LVM thin) + 데이터셋 공유 (NFS) 로 정돈.

1. 배경 + use case

1.1 우리가 만드는 건 무엇인가

HyperCube = GPU workstation 임대 플랫폼
  • 사용자 1명 ↔ 컨테이너 1개 매핑 (replica 없음)
  • 사용자가 컨테이너 안에서 Jupyter / ssh / terminal 로 작업
  • 컨테이너는 long-running session, 사용자가 stop / start 통제
  • GPU slice (MIG 또는 통째) 가 컨테이너에 할당
  • 유사 모델: Paperspace, RunPod, Vast.ai, Lambda Labs, Jarvislabs

K8s 같은 service orchestration 이 아님. autoscaling, multi-replica, load balancer, 자동 healing 모두 우리 use case 에 무의미. 표준 패턴은 backend (scheduler) + agent (per-host docker control) + 컨테이너 (사용자 workspace) 구조. K8s 가 해결하는 문제 (다 host scheduling, service mesh, HA) 는 우리에게 없음.

1.2 현 상태 문제

컨테이너 생성 시 cpu_quota·memory_limit·disk_quota 중 어느 것도 명시 안 함. Docker default = unlimited → 한 컨테이너가 host 자원을 다 점유 가능.

구체적 문제
  • 한 사용자가 학습 시 RAM burst → 다른 컨테이너 OOM 으로 죽음 (noisy neighbor)
  • KPI 의 "메모리 2.40 %" 는 사실상 host 전체 15.5 GB 중 386 MB → "내 quota 의 X%" 라는 운영자 직관과 불일치
  • 한 사용자가 host 디스크를 100 GB 데이터셋 + checkpoint 들로 채움 → docker daemon write 실패 → 전체 서비스 down
  • 자원 회계 / 과금 측정 불가

목표는 (a) 컨테이너 요청 시 자원 한도를 1급 시민으로 편입, (b) 템플릿별 근거 있는 default 를 추천, (c) KPI 가 "quota 의 X%" 라는 명확한 의미를 갖게 함, (d) workspace 디스크를 LVM thin volume 으로 컨테이너별 완전 격리 (MIG-level 단절).

3. 변경 범위

3.1 Template 모델 — 권장 한도 필드 추가

각 워크스페이스 템플릿에 baseline 한도 저장.

# backend/apps/templates/models.py
class Template(models.Model):
    name = models.CharField(max_length=120)
    image = models.CharField(max_length=240)
    # ... 기존 필드
    recommended_cpu_percent = models.PositiveIntegerField(
        default=400,                  # 4 cores = 100*4
        help_text="100 = 1 vCPU. 0 = unlimited",
    )
    recommended_memory_mb = models.PositiveIntegerField(
        default=16384,                # 16 GB
        help_text="MB 단위. 0 = unlimited",
    )
    min_cpu_percent = models.PositiveIntegerField(default=200)   # 2 cores
    min_memory_mb   = models.PositiveIntegerField(default=4096)  # 4 GB (이미지가 못 돌아가는 하한)

3.2 Request 스키마 — 사용자 override 허용

# backend/apps/containers/serializers.py
class ContainerRequestSerializer(...):
    # 새 옵션 필드 — 미지정 시 template.recommended_* 사용
    cpu_percent = serializers.IntegerField(required=False, min_value=0, max_value=10000)
    memory_mb   = serializers.IntegerField(required=False, min_value=0)

    def validate(self, data):
        tmpl = data.get('template')
        cpu  = data.get('cpu_percent',  tmpl.recommended_cpu_percent  if tmpl else 0)
        mem  = data.get('memory_mb',    tmpl.recommended_memory_mb    if tmpl else 0)
        if tmpl and cpu < tmpl.min_cpu_percent:
            raise serializers.ValidationError({'cpu_percent': f'최소 {tmpl.min_cpu_percent} 필요'})
        if tmpl and mem < tmpl.min_memory_mb:
            raise serializers.ValidationError({'memory_mb': f'최소 {tmpl.min_memory_mb} MB 필요'})
        data['cpu_percent'], data['memory_mb'] = cpu, mem
        return data

3.6 Agent host capacity 자동 수집 (system_info)

추천값을 host 사양에 동적으로 맞추려면 backend 가 각 host 의 정적 capacity (cpu_cores, ram_total, disk_total, lvm_pool_size, gpu_count 등) 를 알아야 함. 하드코딩 X — agent 가 자동 보고.

현 상태
  • ✓ system_metrics 메시지로 시계열 메트릭 (CPU%, mem used 등) 은 보고 중 (SystemMetricsHistory)
  • ✗ 정적 host capacity (cpu_cores, ram_total_mb, disk_total_gb 등) Agent 모델 저장 필드 없음
  • ✗ scheduler 없음 — 사용자가 target_agent 수동 지정 (ContainerRequest.target_agent)

이번 PR 에 추가

# backend/apps/agents/models.py — Agent 모델 정적 capacity 컬럼 추가

Agent 측 동작 (별도 repo, Issue 로 요청)

  • agent 시작 시 1회 + 일정 주기 (예: 1시간) 마다 host 사양 수집:
    • os.cpus().length, os.totalmem() (Node.js)
    • df -B1G /, lsblk -d
    • lvs vg0/thin_pool (pool 존재 여부 + 크기)
    • ethtool {iface} (NIC speed)
    • df -T /var/lib/docker (filesystem)
  • 새 message type capacity_report 또는 기존 system_metrics 첫 frame 에 포함
  • backend 가 받아서 Agent 모델 컬럼 갱신

이로써 host 추가 시 agent install 한 줄 만으로 backend 가 자동으로 host 사양을 알게 됨. 하드코딩 / 별도 조사 / 운영자 입력 모두 불필요.

backend scheduler (PR 후속)

  • 지금은 사용자가 target_agent 수동 지정 — 1~2 host 환경에선 OK
  • host 늘면 backend 가 자동 선택해야:
    • GPU 빈자리 (gpu_slice 의 allocated 안 된 것)
    • RAM 여유 (host 의 ram_total - 그 host 에 띄운 컨테이너들 limit 합)
    • workspace pool 여유 (lvm_pool_size - 그 host 의 volume 합)
    • 사용자 affinity (이전에 쓰던 host 우선)
  • 현 PR 범위 아님 — Phase 1 (3~10 host) 에 추가

3.7 워크스페이스 디스크 격리 — LVM thin volume

각 컨테이너에 가상 block device (LVM thin volume) 를 1 개 발급. 컨테이너는 자기 volume 만 봄 → host 디스크 구조 / 다른 컨테이너 작업물 노출 0. MIG 가 GPU 를 partition 하듯 LVM thin 이 디스크를 partition.

구조

host /
├─ /var/lib/docker            # Docker image / overlay layer (host 공유, 변경 없음)
├─ /dev/vg0/                  # LVM Volume Group
│  └─ thin_pool               # thin pool (예: 2 TB, host disk 의 대부분)
│     ├─ cid_05eddec          # 컨테이너별 thin volume (가상 100 GB)
│     ├─ cid_a1b2c3d4
│     └─ ...
├─ /var/lib/hypercube/workspaces/
│  ├─ 05eddec/                # mount point per-container
│  └─ a1b2c3d4/
├─ /mnt/datasets              # NFS read-only (공유 데이터셋)
└─ /mnt/models                # NFS read-only (HuggingFace cache 등)

Agent 측 책임 (별도 repo, Issue 로 요청)

  • 컨테이너 생성 시:
    1. lvcreate -V {gb}G -T vg0/thin_pool -n cid_{cid}
    2. mkfs.ext4 /dev/vg0/cid_{cid}
    3. mount /dev/vg0/cid_{cid} /var/lib/hypercube/workspaces/{cid}
    4. docker run 에 -v /var/lib/hypercube/workspaces/{cid}:/workspace + -v /mnt/datasets:/datasets:ro + -v /mnt/models:/models:ro
  • 컨테이너 삭제 시 unmount → lvremove vg0/cid_{cid}
  • 실패 rollback (mkfs 후 mount 실패 시 lvremove)
  • thin pool 사용량 모니터링 (over-provision 위험 — 모든 volume 합 > pool size 가능)

Backend 측 변경

  • Template 에 recommended_workspace_gb, min_workspace_gb 추가
  • ContainerRequest 에 workspace_gb 옵션 필드
  • Container 모델에 workspace_gb_limit, workspace_device 저장
  • Agent payload 의 create_container 에 workspace.sizeGb 전달
  • current-metrics 응답에 workspace 디스크 사용량 (workspace.used, workspace.total) 포함

왜 LVM thin 인가

  • 완전 격리 — 컨테이너는 자기 가상 disk 만 봄, host 파일시스템 안 보임
  • thin provisioning — volume 100 GB 줘도 실제 쓴 만큼만 host 점유 (over-provision 가능)
  • 단순 — Linux 표준, 운영팀 대부분 익숙, kernel module 추가 불필요
  • 가벼움 — RAM 사용 없음 (ZFS 의 ARC cache 1~4 GB 와 대조)
  • 확장 시 호환 — 미래 K8s 도입 시 OpenEBS LocalPV 의 backend 로 그대로 활용 가능

대안 비교 (참고)

방식 격리 운영 복잡도 선정 여부
bind-mount + XFS quota 약함 (host dir 노출) 낮음 ❌ 격리 부족
LVM thin volume 강함 (block-level) 중간 ✅ 선정
ZFS dataset 강함 + 압축/snapshot 중간 + 학습 ❌ 운영팀 친숙도 + RAM 사용
devicemapper Docker 강함 높음 (deprecated) ❌ 비추천

4. 추천 알고리즘

Phase 1 — agent capacity 기반 동적 공식 (지금 적용)

하드코딩 X. backend 가 각 host 의 agent 보고 capacity + 가정 동시 사용자 수 로 추천값 동적 계산. 운영팀이 정하는 건 "템플릿 weight (자원 비중)" 와 "host 당 동시 사용자 수" 두 가지 파라미터만.
공식
# backend 가 agent.cpu_cores, agent.ram_total_mb 활용
host_capacity_cpu  = agent.cpu_cores * 100        # 12 cores → 1200 percent
host_capacity_ram  = agent.ram_total_mb            # 예: 256000 MB
host_capacity_disk = agent.lvm_pool_size_gb        # 예: 3000 GB

# 운영 파라미터 (admin 설정, 호스트 단위)
target_users_per_host = 8                          # 가정 동시 사용자 수
safety_margin         = 0.80                       # 호스트 자원의 80% 만 분배

# 1 사용자 fair-share baseline
fair_cpu_per_user  = (host_capacity_cpu  * safety_margin) / target_users_per_host
fair_ram_per_user  = (host_capacity_ram  * safety_margin) / target_users_per_host
fair_disk_per_user = (host_capacity_disk * safety_margin) / target_users_per_host

# 템플릿 weight 로 분배 (예: PyTorch Jupyter = cpu 1.0 / ram 1.5 / disk 1.0)
recommended_cpu_percent  = round(fair_cpu_per_user  * template.cpu_weight  / 100) * 100
recommended_memory_mb    = round(fair_ram_per_user  * template.ram_weight  / 1024) * 1024
recommended_workspace_gb = round(fair_disk_per_user * template.disk_weight / 10)   * 10
예시 — agent 보고: cpu=24 cores, ram=256 GB, lvm_pool=3 TB
템플릿 weight (cpu/ram/disk) 추천 (8명 동시 가정)
데이터 탐색0.5 / 0.5 / 0.5 1.5 cores · 16 GB · 188 GB
PyTorch Jupyter1.0 / 1.0 / 1.0 3 cores · 32 GB · 375 GB
대규모 학습1.5 / 2.0 / 1.5 4.5 cores · 64 GB · 562 GB
LLM Inference1.5 / 1.0 / 0.5 4.5 cores · 32 GB · 188 GB

→ host 사양 바뀌면 추천값 자동 갱신. 새 host 추가 시 그 host capacity 로 재계산. 운영팀은 template weight 와 target_users_per_host 만 관리.

Template 모델 확장
# backend/apps/templates/models.py
class Template(models.Model):
    name = models.CharField(max_length=120)
    # ...
    cpu_weight  = models.FloatField(default=1.0)   # 자원 비중 (1.0 = fair share)
    ram_weight  = models.FloatField(default=1.0)
    disk_weight = models.FloatField(default=1.0)
    min_cpu_percent  = models.PositiveIntegerField(default=100)   # 이미지 hard floor
    min_memory_mb    = models.PositiveIntegerField(default=2048)
    min_workspace_gb = models.PositiveIntegerField(default=10)
운영 파라미터 (host 별 또는 글로벌)
# backend/apps/agents/models.py — Agent 모델 운영 파라미터 추가
class Agent(models.Model):
    # 기존 capacity 필드 ...
    target_users   = models.PositiveIntegerField(default=4)    # 가정 동시 사용자
    safety_margin  = models.FloatField(default=0.8)            # 자원 분배 비율

운영자는 admin 페이지에서 host 별 target_users 만 조정. 그 외 자동.

Phase 2 — history 기반 동적 추천 (3~6 개월 후)

KPI 의 평균/피크 데이터 활용. 이미 메트릭 수집 중.
  • 지난 30일 메모리 피크 × 1.2 = 추천 limit
  • CPU 평균 × 2 + safety = 추천 quota
  • "최근 N 일간 OOM 회수 ≥ 1" 이면 자동 +20% 상향 알림
  • 사용자 history 부족 (신규) 시 Phase 1 fallback

Phase 3 — LLM 추정 (선택)

노트북 / requirements.txt / 코드 정적 분석. 우선순위 낮음.
  • imports 에 transformers / lightning → 학습 워크로드
  • 모델 카드 (config.json) 의 hidden_size 등으로 메모리 추정
  • 현 단계에선 over-engineering. Phase 2 충분히 검증 후 검토.

5. 기술 검증 — cgroup / Docker

자원 Docker 옵션 동작 주의
CPU hard cap --cpu-quota / --cpu-period quota 도달 시 throttle (kill X) 안전
CPU share (가중) --cpu-shares 경합 시 가중치 분배 한도 아님. 현재 안 씀
메모리 hard limit --memory 도달 시 OOM kill safety margin 20~30% 필수
memory swap --memory-swap = limit 시 swap 비활성 OOM 으로 빠르게 fail → 안전
live update docker update 재시작 없이 변경 이미 update-limits 에서 사용
디스크 용량 (overlay2) --storage-opt size=... devicemapper / btrfs 만 지원 overlay2 에서 안 됨. 우회: LVM thin volume bind-mount
디스크 용량 (LVM thin) lvcreate -V {gb}G + mkfs + mount + -v /vol:/workspace block-level 격리, MIG 단절 thin pool over-provision 모니터링 필요
디스크 I/O rate --device-read-bps 등 I/O bytes/sec 제한 가능. 우선순위 낮음
⚠ OOM kill 주의
  • 메모리 limit 도달 시 컨테이너 SIGKILL → 사용자 작업 손실
  • 대책: (a) 추천값에 safety margin 20~30%, (b) 메모리 사용량 임계 (75%, 90%) 시 alert, (c) KPI 의 warn/danger threshold 와 일치
  • cgroup v2 환경이면 memory.high(soft) + memory.max(hard) 분리 가능 → 점진적 throttle 후 OOM. v1 은 hard 만

  • 회귀 — 기존 update-limits API 동작 그대로 유지
  • KPI 일치 — 한도 명시 후 KPI 의 분모 변경 (host → quota) 정상 반영

8. 위험 / mitigation

  1. OOM kill 로 사용자 작업 손실
    • mitigation: 추천값에 safety margin 20~30%, KPI 85%+ 시 사용자 알림, 자동 limit ↑ 옵션
  2. over-provision (한도 너무 크게 잡힘) → 동시 사용자 수 감소
    • mitigation: admin 의 "host 점유 미리보기", 동시 N명 가정 시뮬레이션
  3. Agent payload 변경으로 구버전 agent 가 한도 무시
    • mitigation: agent 버전 체크 → 구버전이면 backend 에서 update-limits 폴백
  4. 기존 컨테이너 (한도 없음) 의 KPI 의미 혼란
    • mitigation: 카드 chip 에 (unlimited) 표시, 운영팀이 backfill 스크립트로 일괄 적용
  5. cgroup v1 / v2 환경 차이 (memory.high 미지원)
    • mitigation: host kernel 확인 → v2 면 high+max 사용, v1 이면 max 만

9. OOM 방지 hard floor

메모리 limit 이 너무 작으면 컨테이너가 시작도 못 하거나, 시작 직후 OOM kill 로 죽음. 사용자가 임의로 너무 낮은 값을 넣지 못하게 이중 floor 적용.

9.1 두 단계 floor

층위 출처 의미 위반 시
(A) 이미지 hard floor Template.min_memory_mb 등 이 이미지가 idle 상태로 떠있기만 해도 필요한 RSS. 사용자가 절대 못 내릴 한계. API 400 reject. 운영팀이 결정.
(B) 워크로드 safety floor 추천값 × 0.6 (예시 계수) 사용자가 추천보다 낮춰도 안전한 범위. UI warning ("작업 손실 위험"), 저장은 허용.

9.2 추천값 + safety margin

# 기획안 산식
recommended_memory_mb = baseline_workload_peak_mb * 1.25   # 25% safety
min_memory_mb         = max(image_idle_rss_mb,             # 이미지 자체 floor
                            recommended_memory_mb * 0.6)   # 워크로드 floor

예: PyTorch Jupyter 의 idle RSS ≈ 1.5 GB, 추천 16 GB → min = max(1.5, 9.6) = 9.6 GB. 사용자가 9.6 GB 미만 입력 시 UI warning + API reject.

9.3 컨테이너 모델의 anti-OOM 로직

  • 메모리 사용량 KPI 85% 이상 5분 지속 → 사용자에게 알림 ("limit 가까움")
  • 90% 이상 → admin 알림 + 자동 limit ↑ 옵션 (사용자 동의 후)
  • OOM kill 이력 (oom_count) 누적 시 다음 생성 추천에서 ×1.5 자동 적용

9.4 cgroup v2 의 high / max 두 단계

host 가 cgroup v2 라면 memory.high (soft, throttle) + memory.max (hard, OOM) 분리 가능. v1 은 hard 만.

  • memory.high = recommended × 0.9 → 도달 시 throttle (작업은 살아있음, 느려짐)
  • memory.max = recommended × 1.1 → 도달 시 OOM kill (true hard limit)
  • 이 패턴으로 user 가 "느려진다 → 한도 늘려달라" 요청할 시간을 줌
요약 — 이중 floor + 85/90% 알림 + cgroup v2 의 high/max 분리 = OOM kill 거의 0. floor 가 너무 빡빡하면 동시 사용자 수 감소 trade-off 있음. 운영 데이터로 조정.

11. Host 확장 path (1 → 20 host)

GPU workstation 임대 모델은 K8s 같은 service orchestration 없이도 host 수십 대까지 확장 가능. 아래 단계별로 우리 구조에 추가만 하면 됨.

Phase 0 — 현재 (1~2 host)

  • backend (Django) 1 인스턴스
  • agent 가 각 host 에 1 개씩
  • 컨테이너는 backend 가 host 선택 후 agent 에 명령
  • workspace = LVM thin per-host
  • 데이터셋 / 모델 = NFS read-only mount

Phase 1 — 3~10 host

  • host 추가 = agent install 한 줄 — LVM pool 자동 셋업, NFS mount, capacity 자동 보고
  • backend host 선택 scheduler 정교화 (GPU 빈자리 + RAM 여유 + lvm_pool 여유 + 사용자 affinity)
  • NFS HA 도입 (NAS 이중화 또는 keepalived)
  • backend 모니터링 dashboard (모든 host KPI 통합)

Phase 2 — 10~20 host (H100 × 4 × 20 = 80 GPU)

  • backend cluster (HA) — backend 2~3 인스턴스 + PostgreSQL HA
  • WebSocket fan-out 확장 (agent connection 수 ↑)
  • host scheduler 의 GPU-aware 최적화 (MIG slice 효율 배치)
  • 운영자 admin 페이지 강화 (host 별 자원, over-provision 경고)
  • 이 규모도 K8s 없이 가능. Paperspace / RunPod / Vast.ai 가 이 패턴.

Phase 3 — 50+ host (검토만)

  • K8s 도입 검토 — 단 service hosting 으로 use case 가 확장될 때만 의미
  • workstation 임대 모델 유지하면 자체 backend + agent 가 여전히 적합
  • 현 시점에선 over-engineering, plan 안 함
핵심: LVM thin + NFS + 자체 scheduler 구조는 host 20대까지 충분히 scale. K8s 가 풀어야 할 문제 (분산 service orchestration) 가 우리 use case 에 없으므로 K8s 도입을 미래에도 강제할 이유 없음.

12. 결정 사항

12.1 네트워크 한도 — 결정: 도입 안 함

  • 이유 1: airgap + 내부 NAS 환경. 외부 트래픽 거의 없음. NIC 가 거의 항상 여유.
  • 이유 2: ML 워크로드는 burst 가 정상 (데이터셋 sync, 체크포인트 upload). rate limit 잡으면 사용자 작업 자체가 느려짐.
  • 이유 3: CPU / 메모리 / 디스크가 진짜 병목. 거기 먼저 통제.
  • 적용: rate limit X. 누적 RX/TX 모니터링 only (이미 KPI 카드에 있음). admin 알림 — 5 분 평균 > 500 MB/s (NIC 50% 가정) 시 알림. 실측 후 임계 조정.
  • 재검토 트리거: 데이터셋 sync 충돌이 운영 중 실제로 자주 보고됨 → Phase 2 에 rate limit 도입.

12.2 디스크 용량 — 결정: LVM thin volume per-container + NFS 공유

  • 이유 1: 한 사용자가 host 디스크 채우면 docker daemon 까지 죽음 — 최우선 격리 필요.
  • 이유 2: bind-mount 는 host 디렉토리 노출 → 진짜 격리 아님. MIG 마냥 단절 위해 block-level 격리 필요.
  • 이유 3: ZFS 는 더 강력하지만 RAM 비용 + 운영 학습. LVM thin 으로 충분.
  • 적용:
    • workspace = LVM thin volume per-container (가상 100 GB 등)
    • 데이터셋 = /mnt/datasets NFS read-only mount
    • 모델 = /mnt/models NFS read-only mount
    • Docker image / overlay layer = host 공유 (변경 없음)
  • 재검토 트리거: 운영팀이 snapshot / clone 자주 필요 → ZFS 로 마이그.
